# Design 1.3 — a key per message, and a session that heals

> **Status:** adopted 2026-11-20 — the owner chose **two releases** (2.8 symmetric chains, 2.9 DH + post-quantum step); the post-quantum interval (50 messages / 24 h) and the skipped-key limits (48 h, 1,000) stand as proposed.
> **Roadmap:** `docs/ROADMAP-3.0.md` step 1.3 (review task 1.2). Releases 2.8 (symmetric ratchet) and 2.9 (asymmetric + post-quantum step).
> **Builds on:** 1.1 (AAD + sequence numbers, live in 2.6.0) and 1.2 (Ed25519/X25519 identity, live in 2.7.0).

## 1. What is there today (read in the code)

* A live session gets **one AES-256-GCM key** from the hybrid handshake (P-256 ECDH + ML-KEM-768, `poorija-session-v3`, kex-offer/answer/confirm). Every payload of every kind — text, rich, edit, voice, file, sticker, every file chunk — is encrypted under that one key.
* That key is **written to the vault** (`persistSessionKey`) and **revived after a reload** for up to **7 days** (`SESSION_KEY_LIFETIME_MS`). So whoever reads the vault, or the device's memory, at any moment inside those 7 days can open everything the two sides said in that window, in both directions — and everything after, until the next handshake.
* Offline mail: each envelope has its own throwaway key sealed to the contact's prekey (good), but the payload **inside** is still under the session key, and the envelope **carries the session key itself** (`sessionKeyRaw`) so the receiver can open it after a restart. That is the opposite of forward secrecy: the session key travels in every envelope.
* The 1.1 binding already gives every payload a `sid`, a `kind` and a monotonic `seq`, and a replay window — the slots a ratchet needs.

## 2. The design

### 2.1 Chains (release 2.8 — symmetric ratchet)
From the handshake's output, instead of one AES key, both sides derive a **root key** `RK` and two **chain keys**, one per direction:

```
RK, CK_A→B, CK_B→A = HKDF(handshake secret, "poorija-ratchet/1" ‖ transcript)
```
(direction named by the two fingerprints in sorted order, so both sides agree which is which).

For every message sent:
```
MK_n   = HMAC-SHA-256(CK_n, 0x01)     message key, used once
CK_n+1 = HMAC-SHA-256(CK_n, 0x02)     next chain key; CK_n is erased
```
The message is AES-256-GCM under `MK_n` with the 1.1 AAD; `n` is the 1.1 `seq` field's job in a new form: the payload carries `{ n, pn }` (index in this chain, length of the previous one). `MK_n` is erased as soon as the message is encrypted or decrypted.

**What this buys:** a key stolen today opens only messages not yet sent from that chain point, never the ones before it. The 7-day key goes.

**Out of order / lost messages:** the receiver advances the chain to `n`, keeping the skipped `MK`s in a store **encrypted in the vault**, at most **1,000 keys** and at most **48 hours** each (review §1.2), then deleted. A message whose key is neither derivable nor stored is dropped and acknowledged.

**State on disk:** the chain keys (not message keys) are stored encrypted with the other stores, so a reload continues the chain. A message key never touches disk except a skipped one, and only for 48 h.

### 2.2 The DH step (release 2.9 — asymmetric ratchet, heals the session)
Every message carries the sender's current **ratchet public key** (X25519, 32 bytes — the identity v4 curve). When a side receives a new ratchet key from the other, it does:
```
RK, CK_recv = HKDF(RK, X25519(my_ratchet_priv, their_new_pub))
new my_ratchet keypair
RK, CK_send = HKDF(RK, X25519(my_new_priv, their_new_pub))
```
— the Signal Double Ratchet. **Post-compromise security:** an attacker who stole everything at one moment loses it after the next round trip, because each new DH secret uses a private key that did not exist when they stole.

**The post-quantum step (PQ3-style):** every **50 messages or 24 hours**, whichever comes first, the sender attaches an ML-KEM-768 encapsulation to the peer's current ML-KEM ratchet key, and the shared secret is mixed into the next root key update. A recording kept for a quantum computer then has to break ML-KEM as well as X25519 at every one of those points, not just the handshake. (Full SPQR / ML-KEM Braid is roadmap 2.3 of PROTOCOL-ROADMAP, a later step; this is the scheduled variant iMessage PQ3 uses.)

### 2.3 What uses the ratchet
* **Live messages of every kind** (text, rich, edit, space-message, voice, file, sticker) — through `encryptForSession`/`decryptForSession`, which already take a `kind`. The call sites do not change.
* **File chunks:** one message key per **transfer**, from the chain, and chunk keys derived from it by index (`HKDF(MK, "chunk" ‖ index)`), so a 1 GB file does not consume 16,000 chain steps and a resend still works.
* **Offline mail:** the payload inside the envelope is a ratchet message like any other. The envelope **stops carrying `sessionKeyRaw`**; the receiver opens the payload with the chain it holds. If it holds no chain for that sender (first contact, or a lost device), the payload is under a one-off key derived inside the prekey seal (what the prekey seal already provides) — never the session key.
* **Two devices of one account:** one ratchet per **device pair** (`deviceId` already exists), so a phone and a laptop of the same person each have their own chain with each contact. This also closes the 1.1 gap (a frame reflected between one's own devices).

### 2.4 Negotiation and downgrade
* A new cap **`dr1`** (2.8) and **`dr2`** (2.9) in the hello and the handshake. Both sides on `dr1`: the handshake outputs chains instead of a key.
* A contact seen once on the ratchet is pinned (`ratchetPinned`, like `kexPinned` and `aadPinned`); a session with them that offers no ratchet is refused.
* An older app keeps the 2.7 behaviour with a newer one until it updates.

## 3. Order of work
1. `js/crypto/ratchet.js` (ES module, pure, unit-tested in Node): KDF chains, message keys, skipped-key store, serialisation; the DH and PQ steps behind a flag for 2.9.
2. Bridge + session wiring: handshake outputs chains; `encryptForSession`/`decryptForSession` go through the ratchet when `dr1`; storage of chains replaces `persistSessionKey`.
3. Offline: drop `sessionKeyRaw`; payloads in envelopes are ratchet messages.
4. Files: per-transfer key from the chain.
5. Tests, then 2.8 release; then the DH + PQ step as 2.9.

## 4. Tests (each fails on today's code)
* `ratchetfs.mjs` — **forward secrecy:** take the session state from a device after message 10; it cannot decrypt messages 1–9 (their keys are gone), and the vault holds no key that does.
* `ratchetooo.mjs` — messages delivered out of order and with gaps (relay mail behind live) all open once; a skipped key is gone after it is used and after 48 h; more than 1,000 skipped is refused.
* `ratchetpcs.mjs` (2.9) — **post-compromise:** steal the whole state at message 10; after one round trip the thief cannot decrypt message 12.
* `ratchetoffline.mjs` — an envelope no longer contains any session or chain key; mail queued during a restart still opens.
* Unit tests of `ratchet.js` against fixed vectors.
* Full gate on a quiet machine before each release.

## 5. Risks
* **Desync** is the classic ratchet failure: if one side loses its state (cleared storage, a restored backup) the chains no longer match. Limited by: a session that cannot decrypt asks for a **new handshake** (the existing `chat-key-request` path), which starts fresh chains; nothing is lost that the other side can resend.
* **Storage writes:** the chain advances on every message, so its state is written often. It rides the existing debounced encrypted store, like the 1.1 replay window.
* **Multi-device fan-out** multiplies chains (contacts × their devices × my devices). Bounded: chains for a device not seen for 30 days are dropped.
